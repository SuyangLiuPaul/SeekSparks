- **v1.6.46** — **the divine name was being printed as a translator's insertion (task #282).** The report was cosmetic — `主 [雅伟]` on some KWIC lines, `主 [ 雅伟]` with a stray gap on others — and the spacing turned out to be the least of it. **Start with what the bracket MEANS, counted rather than guessed:** every square bracket in `cuvs-yhwh.json` is one of exactly two tokens, `[雅伟]` × 212 and `[基督]` × 17 (`cuvs-yhwh-tr` mirrors it with `[雅偉]`), so the convention is closed and enumerable. Reading the contexts settles what it is: `X[雅伟]` is a **referent gloss** — the word X printed here refers to Yahweh — marking κύριος where an OT quotation had YHWH, and in a handful of OT verses marking a PRONOUN (`我[雅伟]`, `他[雅伟]`) whose antecedent is the Name. `[基督]` is the identical device pointing at the Messiah, and **Matthew 22:44 carries both four characters apart**, which is why they cannot be told apart by styling one as an insertion. **The direction is the whole point:** a supplied word means the target has MORE than the source (`darkness [was] over`), a gloss means the source had something the target LOST. `scripture_markup.dart` had ONE bracket rule — `_suppliedRe` → `supplied` → italic — so the app set 雅伟 in the convention that has meant "the translator added this" since the Geneva Bible, i.e. the reverse of the claim the edition exists to make. **Three consequences, one root.** (1) Semantic, as above. (2) **The clipboard, the one with effects outside the app:** `copyVerseText` resolved the bracket under `keepSuppliedBrackets`, an option that asks "mark the translator's insertions?" — so a reader answering *no* pasted Matthew 22:44 as `主雅伟对我主基督说`, **a divine title Matthew never wrote**, with nothing on screen to show it was never there. Those brackets are now unconditional. The same flattening lived in **five copy-pasted result-list preview pipelines** (search_page ×2, command_pane, originals_sheet, strongs_entry_page) — now one `versePreviewText`, which is precisely why all five carried the same bug. - **v1.6.44** — **the iPad command-line wipe (task #273), fixed as a defect class rather than as three lines.** Tapping an operator chip on iPad put the token in, and then the reader's *next keystroke emptied the field*. **The name of the bug hides the mechanism: `controller.text = x` is not a plain setter.** Flutter implements it as `value = value.copyWith(text: …, selection: TextSelection.collapsed(offset: -1), composing: TextRange.empty)` — so the two-statement idiom (`.text =` then `.selection =`) publishes **two** `TextEditingValue`s, and **the first one carries a selection that describes no position in the text**. On desktop and web the second lands before anything observes the first, which is exactly why this was invisible here and why **1400+ green tests said nothing**. iOS drives text input *asynchronously*: the engine can latch the caret-less state and the platform's echo can arrive *after* the framework has already set the real caret, leaving the field holding a selection that does not describe its text — and the next keystroke is applied against that range, which is why the symptom is "everything disappears" rather than "the caret is in the wrong place". One assignment leaves no window for the two to disagree. **`lib/utils/atomic_text_edit.dart` → `setTextAtomic(text, {caret})`, with two deliberate properties, not incidental ones:** the caret is **clamped into range**, because *an out-of-range selection being unrepresentable* is the invariant the helper exists to hold; and `composing` is **cleared**, because a composing range is measured against the *old* text and can point past the end of the replacement — which matters more here than in a generic app, since `bwh17b_CommandLineFarEast.htm` shows BibleWorks built its command line an entire dedicated three-mode IME (toggled with `<insert>`, a coloured flashing box showing the mode), i.e. **a Bible workbench's command line is an IME surface as a matter of course**, and this app's readers type Chinese into it. **The brief named three sites; the class had eight.** Five more were reachable on iPad and none were in the report: the **recent-search tap on the search page** (the same text-then-selection race), and four that assign `.text` with *no second statement at all* and so simply publish `-1` and leave it — the **settings paste-key field**, the **Gemini key card** (which can fire *while the field is focused*, from a cloud sync), the **feedback prefill**, and the **`+Verse` fallback branch** in the reading pane, whose *other* branch was already atomic. **Verification, honestly separated:** analyze exits **0** (checked by exit code — the first run failed on an info-level `unnecessary_import` that a grep for "error" would have shipped), **1475/1475 green**, and the new tests are proven to *bite*: reverting `_insertToken` to the old two-step fails them with `Expected: <1> Actual: <2>`. - **v1.6.19** — the command line finally speaks the BibleWorks query grammar (bwh16). The workbench pane has been *called* a command line since v1.0.2 while only ever doing a substring scan, so a reader arriving with BibleWorks muscle memory who typed `.love god` searched for that literal string and was told there were no results — and plain `god world` failed the same way for a different reason, because the scan strips spaces, so a two-word search could never match anything and never said why.
