- **v1.6.22** — the small-screen gate stopped arguing with itself, then became a real gate. v1.6.17 gated on `min(width, height) >= 480` — "a phone is a phone in either orientation" — while the copy offered rotation as the one-tap fix. Those are incompatible: a phone's short edge does not change when it rotates, so no rotation could ever satisfy the gate the copy was promising to satisfy. A reader who followed the advice landed on "this screen does not reach two columns in EITHER direction … two need about 736. This screen is 844 x 390", which contradicts itself using its own printed numbers. User: 「把手机横过来并没有改变」. What decides whether the workbench works is whether the columns fit *right now*, so that is now the test — `paneCountFor(width) >= 2` means no advisory, and rotation is offered only when the other dimension genuinely crosses 736, which on a 360x640 phone it does not, and offering it there would be the same broken promise in a smaller size. Then, on the owner's instruction (「不要有仍然继续，就一直是block住」), `Continue anyway` was removed. I had argued the other way when this was specified, and that reasoning holds for a *reminder* — but this is not one: a one-column workbench is not a product the owner wants shipped, and every reader let past forms their opinion of SeekSparks on the worst version of it. The hard block is defensible rather than hostile precisely because there is a real destination behind it (YsWords, phone-first, linked directly) rather than a dead end. A dismissal persisted by v1.6.20 or earlier is deliberately no longer honoured — those readers are exactly the ones who met the self-contradicting advisory and tapped through it, so a stale bit would hold the gate open for the worst-served group. `onContinue` stays on the widget's API: it is what a future setting or a QA build would wire up, and removing it would make restoring the choice a larger change than the decision warrants.
- **v1.6.20** — the command line learned its **verbs** (BibleWorks bwh44, Command Line Shortcuts). v1.6.19 taught it to *search*; it could already navigate; but it still could not change what you were looking at or narrow where you were looking — which is most of what a BibleWorks reader does between searches, and all of it without touching the mouse. Now `d kjv` / `d -kjv` / `d c` / `d english` edit the Browse stack, `p kjv bsb` restacks in the order given, `l gen` / `l matt 5-7` / `l nt` scope the search and bare `l` lifts it, and a bare number is a verse in the chapter you already have open (`3:16` is chapter and verse in the book you are in). `l` is the one that closes a genuine functional hole rather than a fluency gap: `workbench_provider` carried a comment saying the workbench command line "always scans the whole Bible — book scoping lives in the standalone SearchPage", so until now the workbench literally could not search only the Gospels. Four things a naive reading of the help file misses, and they are where the work was: `d` is not one command but a **set editor with four arities** (add, remove, clear, add-a-whole-language); the **search version can never leave the display**, because BibleWorks defines `d c` as "clears all versions except search version", which makes that an invariant of the display and not a default anyone may override; `p` is not `d` three times — it carries an ORDER, which is the one thing the existing version-checkbox dialog cannot express; and a bare number is a **verse**, not a chapter, which is the opposite of what every other Bible app's jump box does. Routing the verbs *first* in `_submit` is safe for the same structural reason v1.6.19's grammar was: every verb is a single ASCII letter followed by whitespace or end-of-line, or a line made only of digits and a colon, and no bundled edition code, book name or query control character has either shape — pinned by a 19-input "not a verb" test group rather than argued, since the failure mode is silent theft of a search someone typed. Every verb echoes what it did, above the results rather than instead of them: a verb's whole effect lands in a *different pane*, which below the three-pane breakpoint is not even on screen, and `d bsb` must not throw away a hit list that took three commands to build. Refusals name the token (`d niv` → "No edition called \"niv\"" plus the list of ones we do have) because falling through to a text search for "d niv" would find nothing and teach a first-day BibleWorks migrant that the verb does not exist. Deliberately not implemented, each recorded with its reason: `d fav`/`o fav` (no favourites UI to name, and their absence removes the `d c` ambiguity), `f c`/`f u`/`f a` (no result checkboxes exist here), `t #` (the help's "current context tab" has no equivalent surface — mapping it onto the Analysis tabs would invent a meaning, and those numbers have already shifted eight times), and the command line's "never forgets" behaviour where ↑ also restores the search version of the recalled line. `l` deliberately stops at chapter granularity: verse granularity is the Verse List Manager's existing job, and its limits are already a corpus snapshot, so the versification caveat is unchanged rather than newly introduced. `parallelMode`/`parallelVersions` moved out of `workbench_page`'s State into `WorkbenchProvider` — a verb typed in the left pane has to reach state the centre pane owns, and a compiler-checked migration beats a published mirror that drifts. Logic in `utils/command_verb.dart`, Flutter-free; 70 core + 23 widget tests against a stand-in edition registry so adding a Bible cannot break the grammar; en/zh-Hans/zh-Hant throughout. One bug caught while writing the tests: the help strings shipped BibleWorks' own examples (`d nas`, `d 太`) and neither resolves here — `nasb` is the code and `太` is a *book*, not a version, so the on-screen help was teaching two commands that fail.
- **v1.6.19** — the command line finally speaks the BibleWorks query grammar (bwh16). The workbench pane has been *called* a command line since v1.0.2 while only ever doing a substring scan, so a reader arriving with BibleWorks muscle memory who typed `.love god` searched for that literal string and was told there were no results — and plain `god world` failed the same way for a different reason, because the scan strips spaces, so a two-word search could never match anything and never said why. Now: `.` AND, `/` OR, `'` lexical phrase, `;` linear phrase, `!` negation, `*`/`?` wildcards, `*N` word gaps, `;N` verse context. Three things a naive reading of the help file misses, and they are where the work was: `!` has two arities (a verse exclusion in AND/OR, but a one-word *position* inside a phrase, which is the documented `'!your *5 house` trap); `*` has two meanings (a character wildcard when glued to a word, a word gap when standing alone); and `;N` is a **verse** context, which quietly makes the window rather than the verse the unit of search. Three deliberate divergences from BibleWorks, each taken as the conservative option: a windowed hit reports *every* participating verse, not just the first, so no verse in the list lacks a search word; a NOT term excludes on the verse rather than the window, so widening a context never silently subtracts results; and the pane echoes the parse back in words ("All of: god, world"), which no competitor does — a grammar whose operators are punctuation is only safe if the reader can see what the punctuation was taken to mean, otherwise a wrong query is indistinguishable from a wrong Bible. The grammar is routed *first* in `runSearch`, which is safe precisely because control characters are first-position only, so no reference, version abbreviation or Strong's expression can be stolen from the branches below it — pinned by a test rather than argued. Highlighting had to learn the grammar too or every command result would have listed verses with nothing marked in them. Two real bugs found by testing against the actual 31,102-verse KJV rather than fixtures: `.?` matched the entire Bible (a bare metacharacter became an any-token slot; now gated on CJK presence, since English wildcards arrive as their own whitespace-delimited piece), and a pointed Hebrew query folded at parse time was compared against unfolded search keys, losing every hit before tokenization. Performance verified on real data, not assumed: `.melchizedek` tokenizes 2 of 31,102 verses; the worst realistic query `.lord god israel*;10` runs in 121ms, which is why the engine is synchronous rather than paying for an isolate hop. Also worth recording: the KJV spells the NT occurrences "Melchisedec", so that search returns 2 verses and not 9 — every corpus figure in the tests was measured, none invented. Logic in `utils/command_query.dart`, Flutter-free; 56 core + 13 real-corpus + 19 widget tests, en/zh-Hans/zh-Hant throughout.

- **v1.6.17** — the small-screen advisory. SeekSparks is a fork of YsWords, the phone Bible reader; v1.6.9 routed phones into the Workbench for visual consistency and thereby made the real problem worse, because below 600px the workbench collapses to its centre pane and a phone got a menu bar over one column of verses — YsWords with extra steps, and a worse copy of its own parent. Silently degrading into the thing you are not is worse than saying "not here". So phones now get one screen explaining what the layout needs, and `Continue anyway` writes a flag that is never unwritten — an advisory, not a lockout, shown at most once ever. Gated on the SHORT edge, never the width: a phone in landscape is 844×390, wide enough to pass a width test but ~320px of text after the 68px of chrome, about eight lines. Rotation is only offered when it is actually true — a 360×640 phone rotated is 640 wide, which clears the app's 600px side-pane gate so two panes *do* appear, with the reading column at 384, under `minReadingPaneWidth` 480; the rule is therefore `portrait && paneCountFor(longEdge) >= 2`, and `paneCountFor` is the same helper the on-screen copy quotes, so rule and message cannot drift apart. Two ambiguities taken conservatively rather than guessed: Flutter web cannot reliably tell a phone from a short desktop window (iPadOS Safari reports as Mac), so the copy states the layout's requirement and the *measured* viewport instead of diagnosing the reader's device — actionable whether the fix is to rotate, resize a window, or move to a tablet; and the YsWords link uses the intl site for all three locales rather than routing zh-Hans to the China build, which would guess where a reader is from what they read. No error icon, no scolding — nothing has gone wrong. New in research this run, from bwh06's "Optimizing the BibleWorks Workspace": BibleWorks hit the same wall on "pad computers with limited space" and answered it the *opposite* way — hide the chrome (column control strips, toolbar, main menu, status bar) and keep all three columns, because chrome is affordances and columns are the product. That makes a hide-chrome toggle the highest-value follow-up (68px back ≈ 25% more text on a landscape phone); it was deliberately not bundled here. Logic in `utils/workbench_fit.dart`, Flutter-free, with the pane constants defined as sums of the real minimums so the figures shown on screen are the layout's own; 16 core + 15 widget tests, en/zh-Hans/zh-Hant throughout.

- **v1.6.15** — Phrase Matching (BibleWorks bwh51) as the seventh Analysis tab. Related Verses shipped two days earlier asks which verses share the most *words*; this asks which repeat the same *sequence*, because a bag of words cannot tell "thus says the LORD of hosts" from a verse that merely contains those five words scattered about — and finding who *quotes* a verse is a question only word order can answer. The gap is the feature rather than a tolerance: 1..G words may be inserted between phrase words, which is what lets Matthew's "and they shall call" still read as Isaiah's "and shall call", and G bounds each step rather than the whole phrase so a 3-word phrase cannot spread across half a verse. A dropped word is allowed too, but only an interior one — dropping an end word would silently turn a length-3 phrase into a length-2 one. Chopping a verse into 3-word windows leaves mostly filler and BibleWorks offers no answer to that, so phrases in more than 1% of what was scanned start unchecked with their verse count on the chip; Accordance's ">50% common words" rule was rejected because it discards "a virgin shall", which is the whole point of Isaiah 7:14. Verified against the real 31,102-verse KJV, not just fixtures: Jer 31:33 → Heb 8:10 then Heb 10:16, Ps 22:1 → Matt 27:46 and Mark 15:34, Isa 7:14 → Matt 1:23, each top of the list; worst case Esther 8:9 at 319ms. Logic in `utils/phrase_match.dart`, Flutter-free; 64 core + 6 real-corpus + 14 widget tests.
